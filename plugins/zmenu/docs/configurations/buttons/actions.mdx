# Actions

Actions are commands executed when a player interacts with a button. zMenu provides 30+ action types for various purposes.

## Basic Usage

```yaml
items:
  my-button:
    slot: 0
    item:
      material: DIAMOND
    actions:
      - type: message
        messages:
          - "&aHello, %player%!"
      - type: sound
        sound: UI_BUTTON_CLICK
```

## Common Options

All actions support the following optional parameters:

### delay

Add a delay (in ticks) before the action is executed. 20 ticks = 1 second.

```yaml
actions:
  - type: refresh
    delay: 10  # Wait 10 ticks before refreshing
```

---

### chance

Set a percentage chance for the action to execute. Combined with `deny-chance-actions` to define fallback actions when the chance fails.

```yaml
actions:
  - type: console-command
    commands:
      - "give %player% diamond 1"
    chance: 50  # 50% chance to execute
    deny-chance-actions:  # Actions to execute if chance fails
      - type: message
        messages:
          - "&cNo luck this time!"
```

**Options:**

| Option                | Type    | Description                                           |
|-----------------------|---------|-------------------------------------------------------|
| `delay`               | Integer | Delay in ticks before execution (20 ticks = 1 second) |
| `chance`              | Integer | Percentage chance (0-100) for the action to execute   |
| `deny-chance-actions` | List    | Actions to execute if the chance check fails          |

**Example with both options:**

```yaml
actions:
  - type: refresh
    delay: 20  # Wait 1 second
    chance: 75  # 75% chance
    deny-chance-actions:
      - type: message
        messages:
          - "&cThe refresh failed!"
```

### broadcast

Send a message to all online players.

```yaml
- type: broadcast
  messages:
    - "&6[Announcement] &f%player% purchased a special item!"
  minimessage: true  # Optional: Use MiniMessage format (default: true)
```

---

### broadcast-message

Send a list of chat lines to every online player.

<Tabs items={["broadcast_message","broadcast message (Alias)"]}>
    <Tab value="broadcast_message">

        ```yaml
        - type: broadcast_message
          messages:
            - "&6[Shop] &f%sender% &7just bought a rank!"
          minimessage: true # Optional, default: true
        ```

    </Tab>
    <Tab value="broadcast message (Alias)">

        ```yaml
        - type: "broadcast message"
          messages:
            - "&6[Shop] &f%sender% &7just bought a rank!"
        ```

    </Tab>
</Tabs>

**Options:**

| Option        | Type    | Required | Description                                                                                       |
|---------------|---------|----------|---------------------------------------------------------------------------------------------------|
| `messages`    | List    | Yes      | The lines sent to every online player. Must be written as a YAML list.                              |
| `minimessage` | Boolean | No       | Parse each line as MiniMessage. Default `true`. Set to `false` to send it as-is. Alias: `mini-message`. |

**Placeholders:** `%sender%` is replaced by the name of the player who triggered the action, `%receiver%` by the name of each player receiving the line.

<CalloutContainer type="info">

<CalloutTitle>Difference with `broadcast`</CalloutTitle>

<CalloutDescription>
`broadcast_message` resolves its placeholders **once**, for the player who triggered it, then sends that same result to everyone — only `%receiver%` varies. [`broadcast`](#broadcast) resolves them **again for each recipient** and supports a `requirements` list to filter who receives the message.

Use `broadcast` when the text must differ per recipient or be filtered, `broadcast_message` for a plain announcement about the player who clicked.
</CalloutDescription>

</CalloutContainer>

<CalloutContainer type="warning">

<CalloutDescription>
Unlike the `message` action, the singular `message` key and a single inline string are **not** accepted: `messages` must be a YAML list. `%player%` substitution and `\n` line splitting are not applied either.
</CalloutDescription>

</CalloutContainer>

### broadcast-title

Display a title and a subtitle to every online player at once. It takes the same options as [`title`](#title), which only targets the clicking player.

<Tabs items={["broadcast_title","broadcast title (Alias)"]}>
    <Tab value="broadcast_title">

        ```yaml
        - type: broadcast_title
          title: "&6&lEVENT"
          subtitle: "&7Started by &f%player%"
          start: 20      # Ticks
          duration: 60   # Ticks
          end: 20        # Ticks
        ```

    </Tab>
    <Tab value="broadcast title (Alias)">

        ```yaml
        - type: "broadcast title"
          title: "&6&lEVENT"
          subtitle: "&7Started by &f%player%"
          start: 20
          duration: 60
          end: 20
        ```

    </Tab>
</Tabs>

**Options:**

| Option     | Type   | Required | Description                                       |
|------------|--------|----------|---------------------------------------------------|
| `title`    | String | Yes      | The title line. See the warning below.            |
| `subtitle` | String | Yes      | The subtitle line. See the warning below.         |
| `start`    | Number | No       | Fade-in duration, in ticks. Default `0`.          |
| `duration` | Number | No       | Time the title stays on screen, in ticks. Default `0`. |
| `end`      | Number | No       | Fade-out duration, in ticks. Default `0`.         |

Placeholders are resolved **once, for the player who triggered the action**, so `%player_name%` refers to that player and not to each recipient — which is usually what an announcement wants.

<CalloutContainer type="warning">

<CalloutTitle>Always write both lines, and all three timings</CalloutTitle>

<CalloutDescription>
`title` and `subtitle` have no default value: omitting one sends the literal text `null` to every player. The three timings default to `0`, which makes the title appear and disappear immediately on most clients. Set them explicitly, as in the examples above.
</CalloutDescription>

</CalloutContainer>

### console-command

Execute a command from the console.

<Tabs items={["console-command","console command (Alias)"]}>
    <Tab value="console-command">

        ```yaml
        - type: console-command
          commands:
            - "give %player% diamond 64"
            - "eco give %player% 1000"
        ```

    </Tab>
    <Tab value="console command (Alias)">

        ```yaml
        - type: "console command"
          commands:
            - "give %player% diamond 64"
            - "eco give %player% 1000"
        ```

        **Options:**

        | Option             | Type    | Required | Description                                                                     |
        |--------------------|---------|----------|---------------------------------------------------------------------------------|
        | `commands`         | List    | Yes      | Commands to execute as the console user                                          |
        | `stop-on-failure`  | Boolean | No       | Stop the remaining commands as soon as one reports a failure. Default `false`. Alias: `stop_on_failure`. |

        **Note:** Supports flexible aliasing for varied command syntax.

        Available aliases: `console-command`, `console-commands`, `commands`, `command`, `console command`, `console commands`, `console_commands` and `console_command`.
    </Tab>
</Tabs>

**Stopping a chain that failed**

By default every command in the list runs, whatever the previous ones did. With `stop-on-failure` enabled, the first command that reports a failure stops the ones after it — so a chain such as "take the money" followed by "grant the rank" can no longer grant the rank when the charge failed.

```yaml
- type: console-command
  stop-on-failure: true
  commands:
    - "eco take %player% 1000"
    - "lp user %player% parent add vip"
```

<CalloutContainer type="warning">

<CalloutTitle>Why it is off by default</CalloutTitle>

<CalloutDescription>
Bukkit returns a failure both for a command that does not exist **and** for a command whose executor returned `false` — which many plugins do simply to print their usage. Enabling this option blindly can therefore stop a chain that was working. Test each chain before turning it on.
</CalloutDescription>

</CalloutContainer>

### random-player-command

<CalloutContainer type="info">

<CalloutTitle>zMenu+</CalloutTitle>

<CalloutDescription>
This action requires [zMenu+](https://minecraft-music-inventory.com/resources/zmenu.music.331).
</CalloutDescription>

</CalloutContainer>

Execute a random selection of commands as the player from a list. The commands are selected **without replacement** (no duplicates in a single execution).

```yaml
- type: random_player_command
  commands:
    - "say I got option 1!"
    - "say I got option 2!"
    - "say I got option 3!"
    - "say I got option 4!"
  amount: 1               # Number of commands to randomly execute (default: 1)
  command-in-chat: false   # Optional: execute via chat instead of dispatch (default: false)
```

**Options:**

| Option | Type | Default | Description |
|--------|------|---------|-------------|
| `commands` | List | Required | List of commands to randomly select from |
| `amount` | Integer | `1` | Number of random commands to execute |
| `command-in-chat` | Boolean | `false` | If `true`, sends via `player.chat()`; if `false`, dispatches as command |

**Aliases:** `random_player_command`, `random_player_commands`, `random-player-command`, `random-player-commands`

## Data Actions

### data

Modify player data values.

```yaml
- type: data
  action: SET       # SET, ADD, SUBTRACT, MULTIPLY, DIVIDE, REMOVE
  key: "coins"
  value: "100"
  math: true        # Optional: enable math expressions
```

**Options:**

| Option | Type | Description |
|--------|------|-------------|
| `action` | String | The operation to perform (see table below) |
| `key` | String | The player data key to operate on |
| `value` | String | The value to use (supports placeholders) |
| `math` | Boolean | Enable math expression evaluation in `value` (default: `false`) |
| `seconds` | Long | If set, store the value for only this many seconds before it expires |

**Actions:**

| Action | Description | Example |
|--------|-------------|---------|
| `SET` | Set to specific value | `value: "100"` |
| `ADD` | Add to current value | `value: "50"` |
| `SUBTRACT` | Subtract from current | `value: "25"` |
| `MULTIPLY` | Multiply current value | `value: "2"` |
| `DIVIDE` | Divide current value | `value: "2"` |
| `REMOVE` | Remove the key entirely | - |

**Math expressions:**
```yaml
- type: data
  action: ADD
  key: "total"
  value: "%zmenu_player_value_base%*1.5"
  math: true
```

**Temporary data (expires after N seconds):**
```yaml
- type: data
  action: SET
  key: "cooldown"
  value: "1"
  seconds: 86400   # Expires after 24 hours
```

## Item Actions

These actions give or take items directly from the menu or the player's inventory. They are perfect for shops, kits or reward systems.

### set_item

Place an item in one or several slots, either in the menu or in the player's inventory.

<Tabs items={["set_item","set-item (Alias)"]}>
    <Tab value="set_item">

        ```yaml
        - type: set_item
          slot: 13              # or slots: [13, 14, 15]
          in-player-inventory: false  # false = menu (default), true = player inventory
          dupe-protection: true       # default: true
          item:
            material: DIAMOND
            name: "&bReward"
        ```

    </Tab>
    <Tab value="set-item (Alias)">

        ```yaml
        - type: set-item
          slot: 13
          item:
            material: DIAMOND
            name: "&bReward"
        ```

    </Tab>
</Tabs>

**Options:**

| Option                | Type            | Default | Description                                                        |
|-----------------------|-----------------|---------|--------------------------------------------------------------------|
| `slot`                | Integer         | -       | The slot to set (use `slots` for several slots)                    |
| `slots`               | List            | -       | The list of slots to set                                           |
| `in-player-inventory` | Boolean         | `false` | Place the item in the player's inventory instead of the menu       |
| `dupe-protection`     | Boolean         | `true`  | Protect the placed item against duplication                        |
| `item`                | Item            | -       | The item to place (can also be defined inline at the action level) |

Available aliases: `set_item`, `set-item`.

## Action Order

Actions execute in the order they're listed. If you need to close the inventory after a teleport, put `close` before `teleport`:

```yaml
actions:
  - type: close
  - type: teleport
    world: "world"
    x: 0
    y: 100
    z: 0
```

## Using Actions in Requirements

Actions can also be used in `deny` and `success` blocks of requirements:

```yaml
click-requirement:
  vip-check:
    requirements:
      - type: permission
        permission: "server.vip"
        deny:
          - type: message
            messages:
              - "&cYou need VIP!"
    success:
      - type: message
        messages:
          - "&aAccess granted!"
```
